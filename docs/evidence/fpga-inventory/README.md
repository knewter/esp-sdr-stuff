# FPGA inventory and feasibility checkpoint

Evidence classes: **read-only host enumeration**, **reviewed primary designs** and **calculations**. These are separate from unperformed FPGA transport and RF measurements.

## Current observations

[Host survey](host-survey.json) was generated by `python3 tools/inspect_fpga_host.py`. The script reads sysfs descriptors/state and checks command availability; it never opens serial ports, maps BARs, changes drivers or configures an FPGA. USB serial numbers and physical BAR addresses are omitted.

- A PCI endpoint at `05:00.0` presents `dabc:1017`, subsystem `1af4:a001`, class `020000`. It is unbound, `enable=0`, with current **8 GT/s ×4** and advertised maximum **8 GT/s ×8**. BAR0 is a 2 KiB aperture, BAR2 a 512 MiB aperture. These are address windows, **not RAM measurements**.
- No current USB descriptor identifies a Forgix/RP235x board or a recognized JTAG programmer. Custom firmware can use arbitrary descriptors; this is not proof the board is physically absent. The FT232R device remains unrelated/unknown and was not opened.
- `vivado`, `efx_run`, `openFPGALoader`, `openocd`, `picotool`, `litex_server` and `mpremote` were absent from PATH at capture time. This is a command-availability check, not an exhaustive search of the filesystem.
- No FPGA configuration, register read/write, DMA, JTAG scan or power cycle was attempted.

## Forgix design versus the actual board

The user reports owning an **Adiuvo Forgix**. The physical revision, oscillator marking, installed MCU firmware, USB identity and edge-pin availability have not been inspected.

The [official Forgix specifications](https://forgix.tech/) list RP2354, Trion T8F49, USB 1.1, APS1604M PSRAM, an external oscillator, 3.3 V I/O and 1.1 V FPGA core. These are product specifications rather than measurements of this user's board.

The [Adiuvo schematic at revision c1d83e3](https://bitbucket.org/adiuvo-engineering/forgix_public/raw/c1d83e3e6ad10fa1c5a927731b1e4f54e771bf0f/Schematic/RP2350_FPGA_eensy.pdf) is dated February 24, 2026 and has a blank drawing revision. Its hash and reviewed repository revisions are in [source metadata](source-revisions.json). The drawing identifies **T8F49I2X** and wires PSRAM to the **RP QSPI** controller. It does not expose a direct FPGA-to-PSRAM bus. Oscillator part `ECS-2520MV-xxx-xx` is a placeholder, not a frequency specification.

[LiteX's pinned platform](https://github.com/litex-hub/litex-boards/blob/10debf146d433ce8ac8aedcac84e97d252ff4d5b/litex_boards/platforms/adiuvo_forgix.py) instead selects **T8F49C2**, assumes **32 MHz** at FPGA **B4**, and sets FPGA banks to 3.3 V. Confirm silicon grade and oscillator against the physical board before compiling its target. Differences must be resolved explicitly, not silently treated as equivalent revisions.

The [upstream developer's tested SPIBone flow](https://github.com/enjoy-digital/aduivo_forgix_test/tree/e7c71b750ca61690a70bc79ebd6ff5fbc65cedad) loads a passive-SPI FPGA image from MicroPython and reuses a bidirectional three-wire bus. Its reported validation belongs to the upstream assembly, not this one. Pin mappings agree with the reviewed schematic:

| Internal function | RP GPIO | FPGA ball |
| --- | ---: | --- |
| Config/SPIBone chip select | 1 | G3 |
| Config/SPIBone clock | 2 | F3 |
| Config input / bidirectional SPIBone data | 3 | F2 |
| FPGA reset | 4 | G4 |
| FPGA done | 5 | F4 |
| FPGA status | 6 | A4 |
| Oscillator enable | 19 | oscillator enable input |

This internal bus belongs to the RP. Do not tie an ESP output directly to it while the RP drives the same signal. The later ESP-to-FPGA link should use verified spare edge I/O with one defined driver per signal. The reference `--with-demo-io` deliberately drives edge outputs and is unsuitable for a first trial with external equipment attached.

[Efinix T8 datasheet v5.5](https://www.efinixinc.com/docs/trion8-ds-v5.5.pdf), pages 4–5, specifies 24 memory blocks totalling **122,880 bits (15 KiB)**, eight multipliers, 33 GPIO and one simple PLL for the F49 package. It has no dedicated JTAG pins. Do not infer a generic dedicated-JTAG bring-up route from the larger-package development kits.

## PCIe card: promising host link, unverified sample interface

Neighboring `fpga-research-site` documentation associates this endpoint with **Alibaba Cloud AS02MC04**, silkscreen **R1291-F9003-02**, and **XCKU3P-2FFVB676I**. Its README declares CC BY 4.0; these details are attributed local notes, not newly verified board markings. No text or images from that project were copied here.

[Julia Desmazes' first-hand AS02MC04 investigation](https://essenceia.github.io/projects/alibaba_cloud_fpga/) independently reports this configurable PCI identity, six-pin JTAG access, and a usable clock/constraint investigation. It also reports I/O voltage mismatches in community constraints. That reinforces the need to measure VREF and confirm this card's revision; it does not supply proof for our wiring.

The board's exact silicon grade, accessible GPIO, bank voltages, oscillator pins/frequencies, configuration storage and recovery remain physically unverified. Local notes report no external DRAM and about 3.3 MB on-chip storage, but PCI BAR size cannot substantiate that claim. Even if the PCI link is ample, there is currently no verified ESP-to-card input bus, host driver or reversible programming path.

## Capacity calculations

[Budget JSON](budget.json) is reproducible with `python3 tools/fpga_budget.py`. All rates below exclude framing, transaction gaps, processing and host overhead; they are mathematical bounds, not benchmarks. [Raspberry Pi's datasheet §12.7](https://datasheets.raspberrypi.com/rp2350/rp2350-datasheet.pdf) specifies the RP controller as **12 Mb/s full-speed USB**: at most **1.5 MB/s wire rate**, with lower useful application payload.

| Sample rate | 8+8-bit packed IQ | 10+10-bit packed IQ | 32-bit SRAM words | Maximum original-chip window |
| --- | ---: | ---: | ---: | ---: |
| 16 MS/s | 32 MB/s | 40 MB/s | 64 MB/s | 1.02375 ms |
| 40 MS/s | 80 MB/s | 100 MB/s | 160 MB/s | 0.4095 ms |
| 80 MS/s | 160 MB/s | 200 MB/s | 320 MB/s | 0.20475 ms |

At 80 MS/s with packed 20-bit pairs, Forgix USB is **over 133 times too small before overhead**. No finite FIFO solves that sustained mismatch. Even all 15 KiB of T8 memory would fill in **76.8 µs** without drainage. PSRAM is a potential RP-managed queue; assuming it is a high-speed FPGA sample store contradicts the reviewed wiring.

Decimation factors 16, 64, 128 and 256 reduce 200 MB/s to 12.5, 3.125, 1.5625 and 0.78125 MB/s respectively. Factor 128 still exceeds the USB wire bound; factor 256 has only a mathematical chance after actual transport/processing validation. Anti-alias filtering must precede decimation. Neither decimation nor downstream buffering recovers samples that the ESP never captured.

A maximum 16,380-pair snapshot occupies 32,760 bytes at 8+8 bits or 40,950 bytes at packed 10+10 bits. At the USB wire bound alone, drainage takes at least 21.84 or 27.3 ms, respectively. It also exceeds a T8-only FIFO. Use smaller snapshots or an explicitly benchmarked RP queue.

An assumed 16-bit spectrum vector at 10 frames/s costs 5,120 / 20,480 / 40,960 bytes/s for 256 / 1,024 / 2,048 bins, before headers. That is a plausible **control/spectrum** role to test, not measured performance.

## Original ESP32 route selected for evaluation

The [pinned original-chip receiver](https://github.com/ESPARGOS/esp-sdr/blob/550fadea4d00a9e26ce921c5832167becb3dc20c/main/targets/esp32/receiver.c) reserves a **64 KiB dump aperture** at `0x3ffe8000`, caps output at 16,380 pairs, takes a bounded acquisition, verifies sentinels, and packs output in place before sending UART data. It does not implement an external continuous sample bus. Peripheral DMA access to that reserved SRAM during RF ownership must be tested rather than assumed.

The bounded candidate is **capture → validated copy/pack → ordinary ESP SPI DMA → FPGA FIFO/counters/trigger or decimator → RP SPIBone/USB host**. Start with completed small snapshots; retain gaps explicitly. [ESP-IDF v5.4 SPI documentation](https://docs.espressif.com/projects/esp-idf/en/v5.4/esp32/api-reference/peripherals/spi_master.html) gives an ideal one-line write payload of clock/8 (10 MB/s at 80 MHz) and details routing/timing limitations and transaction overhead. The documented SPI3 IO_MUX pins are CS5/SCLK18/MISO19/MOSI23; their availability on the actual ESP carrier is unknown. Begin slower after both boards' physical labels and voltage are confirmed.

An I2S DMA or parallel LCD output is another firmware experiment, not a connection from the radio ADC straight to an FPGA. The radio dump engine still owns capture. [eSpDR at the pinned S3 revision](https://github.com/h0m3us3r/eSpDR/tree/41a0ffe279119df942e4a9e892dc19d196e1c952) relies on both S3 cores, dedicated GPIO instructions, SIMD packing, sixteen data wires, a forwarded 20 MHz clock, FPGA compression, DDR and FT600 USB 3. Those mechanisms do not port directly to original LX6 or Forgix.

## Decision and next physical inputs

**Current decision:** Forgix is ruled out as a direct raw 80 MS/s USB replacement by documented capacity. It remains a candidate for bounded buffering, event counting, timing, triggering or filtered lower-rate output. The PCIe card is a separate bring-up project with potentially adequate host bandwidth; its current enumeration proves no sample transport. A separate S3 front end remains the closest architectural match to eSpDR if continuous wideband reception becomes the priority.

This is a **partial feasibility decision**. Sustained rates, CRC/sequence integrity, stalls and RF continuity have not been measured. The proposal stays open.

Physical inputs needed to proceed:

1. Connect Forgix by USB and identify it by an unplug/replug delta. Provide its board revision and readable oscillator/FPGA markings (or the exact accompanying schematic/BOM revision). Establish current RP firmware and preserve it before replacement.
2. Confirm exposed ESP and Forgix edge pins, common ground, actual I/O voltage and clock source. Make the ESP data link only after the mapping is checked; no wiring is performed by software.
3. For the PCI card, confirm markings and a JTAG adapter with the correct target-voltage support. Map GND/VREF with measurements, then perform a read-only chain scan before selecting constraints or programming. Establish a cold-cycle recovery method before loading a volatile bitstream; host power cycling requires user action.

Once Forgix is connected and identified, the upstream CPU-less SPIBone identifier/scratch test is the first control-plane milestone. It is not the throughput test. Add an FPGA PRBS/counter FIFO and RP binary bridge, then test 1/10/20/40 MHz candidate clocks at bounded rates for 60 seconds each, with sequence/CRC totals, FIFO high-water mark, overruns, host stalls and a deliberate 100 ms host pause. Gate RF integration on zero unexplained integrity errors and a measured payload margin. No script selecting a guessed serial device or installing a blind PCI driver was created.
