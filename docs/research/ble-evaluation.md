# A bounded owned BLE experiment

This is decoder preparation and source-control research, not proof of ESP32
reception. The burst proposal's four hardware tasks remain open.

## Sources and independent checks

Bluetooth SIG [Core 6.3, Vol 6 Part C, 4.2.1](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core_v6.3/out/en/low-energy-controller/sample-data.html)
publishes a complete channel-38 ADV_NONCONN_IND bitstream, including CRC and
whitening. `tests/test_ble_decode_iq.py` transcribes this independent vector;
the packet fixture is not generated by the decoder. The tests verify CRC,
whitening and a modulated version of that packet with frequency offset,
conjugation and noise. The modulation is synthetic. Corrupted and truncated
packets must fail. Separate generated packets test exact owned AD matching.
The [link-layer specification](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core_v6.3/out/en/low-energy-controller/link-layer-specification.html)
defines chronological bit ordering, the advertising access address, whitening
initialization and advertising CRC initialization.

The [BlueZ advertising API](https://bluez.readthedocs.io/en/latest/advertising-api/)
registers structured advertisements and exposes instance counts and lifetimes.
Registration acceptance does not report RF packet counts. `ActiveInstances`
counts advertising registrations, not completed events. Duration/timeout values
govern configuration lifetimes; userspace registration timestamps do not prove
precise RF start/stop times. Do not call 100 registration episodes 100 emissions.

The [Linux monitor packet header](https://github.com/torvalds/linux/blob/master/include/net/bluetooth/hci_mon.h)
allows observing HCI control traffic separately from the BlueZ API.
`tools/ble_hci_monitor.py` opens only a read-only monitor socket; it never sends
controller commands. It stores a strict whitelist: advertising intervals,
channel map, PHY, enable/disable, command status, exact owned-marker match in
controller advertising-data configuration, and optional controller-reported
completed extended advertising events. All addresses and advertising bytes are
discarded before storage. An explicit Linux `sockaddr_hci` monitor-channel bind
opened successfully and was closed without receiving while the source was off
during preparation on 2026-10-01. This is access feasibility, not a measurement
of any emission. The first implementation used a Python HCI address tuple,
which silently selected the raw channel on this host; its zero-frame results
are invalid as monitor evidence. The corrected tool uses the explicit channel
field because [CPython 3.14's tuple converter](https://github.com/python/cpython/blob/3.14/Modules/socketmodule.c)
does not populate it.

## Source and packet budget

`tools/ble_owned_source.py` registers manufacturer test identifier `0xffff`
with the independently chosen 12-byte ASCII marker `ESP-SDR-EVAL`. Its AD
structure is `0fffffff4553502d5344522d4556414c`: length 15 includes AD type,
company identifier and marker; the length octet makes 16 bytes total.

The source can request equal minimum/maximum intervals with `--interval-ms`
(default 100 ms; bounded 20 to 10,000 ms). The current
[BlueZ primary API documentation](https://github.com/bluez/bluez/blob/master/doc/org.bluez.LEAdvertisement.rst)
defines those properties. A requested interval is recorded separately from
controller configuration and actual RF timing. HCI monitoring must verify the
accepted interval; it still cannot supply an independently counted RF denominator.

A minimal legacy packet containing that AD has 6 address bytes, 16 advertising
data bytes, a 2-byte PDU header, 3-byte CRC, 4-byte access address and 1-byte
preamble: **32 bytes / 256 microseconds at LE1M**. BlueZ/controller-added AD
fields can increase duration. A full 16,380-sample snapshot covers 1,023.75 us
at 16 MS/s and 409.5 us at 40 MS/s; 204.75 us at 80 MS/s is too short even for
the minimal marker packet. Sampling duration does not establish analog bandwidth.

The bounded decoder resamples nominal 16/40/80 MS/s input to 4 MS/s, estimates
carrier offset from access-address correlation, tests symbol timing/polarity,
dewhitens on the specified channel and requires a matching 24-bit CRC before
classifying any packet. Foreign addresses, names and payloads are never returned.
Only an exact complete owned manufacturer AD structure qualifies as owned.
LE2M, coded PHY, extended advertising, hopping sessions and encrypted payloads
are outside this decoder.

## Physical gate

Use at least three paired source-on/source-off trials with pinned receiver
settings, then decode saved private IQ. A valid complete owned packet establishes
that payload's reception; it does not establish a general packet hit rate.
Publish payload comparison, settings, hashes, timing and redacted plots; keep
original raw RF private unless it is independently inspected as solely owned.

The proposal still requires at least **100 counted deliberately emitted events**
and a missed-event denominator. If this controller does not provide sufficient
event ground truth, use an independently counted transmitter/monitor; the gate
remains open rather than changing its meaning. HCI/controller counts, when
available, must identify whether they count advertising events, per-channel
packets or other units; a monitor receives no independent RF confirmation.

## Reproduce host checks

```sh
python3 -m pip install -r tools/requirements-ble.txt
python3 -m unittest discover -s tests -p 'test_ble*.py' -v
```

Twelve tests passed during preparation. No real IQ input was used in these tests.
The source-lifecycle regression simulates BlueZ releasing an advertisement on
unregistration, and verifies that all three subsequent episodes still remove
their own registration. This is simulated control behavior, not RF evidence.
The recorded host used Python 3.14.7, NumPy 2.5.2, SciPy 1.18.0 and
dbus-next 0.2.3. The source and monitor require Linux/BlueZ; packet/decoder
tests have no Bluetooth-device dependency.
